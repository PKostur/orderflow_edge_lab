# Raw-material inventory behind the status of research/payoff-geometry-v1-1

Method: read-only inspection of the checked-out repository (no shell, no git history commands). All "sources" below are repo-relative file paths I read; there are no web URLs. Labels: RAW = unaggregated observations or per-day/per-trade records; DERIVED = computed from raw by code; SUMMARY = statistics or prose only. Anything I could not confirm is marked UNCONFIRMED.

Important limits of this inspection: (1) the local clone is shallow (`.git/shallow` lists 6 boundary commits), so commit order versus first-data timestamps could not be checked here and must be done on a full clone or through the GitHub API; (2) GitHub Actions artifacts, run logs and the user's local folders cannot be seen from the repo, so their contents are inferred from workflow YAML and scripts only.

## 1. Where the raw inputs and raw outputs of the forward watches live

### Takeaway
The forward watches keep almost no raw input. Every run re-downloads exchange bars and funding, recomputes the whole forward period in memory, and uploads ONE report JSON per watch whose richest raw-ish content is a per-day return series (per leg or book). Exchange bars, funding prints, per-day positions/weights and fills are not retained anywhere in the repo or in the artifacts. Only fade24 (trade rows), near-miss/tradfi (config hashes) and the news / liquidation / Hyperliquid-vault collectors (true append-only ledgers, in a 90-day artifact chain) keep more.

### Cited Findings

Blend and the sibling watches in one workflow:
- `.github/workflows/multi-premia-blend-v1.yml`, job `watch`, runs 8 modules and uploads artifact `multi-premia-blend-v1` containing exactly: `report.json` (blend), `human_report.json` (H5/H10/V_ALL), `zoo_mirror_report.json`, `prop_paper_report.json`, `paper_account_report.json`, `paper_fill_scenarios.json`, `fast_gates_report.json`, `tom_forward_report.json` (all under `artifacts/multi_premia_blend/`). ### Inferences
- A professional cannot re-run a forward day from retained inputs: the only way to re-derive the blend's 16-day -2.79% is to re-fetch MEXC bars and funding now. If MEXC revises or drops bars/funding (or a coin delists), the replayed history silently changes and no earlier vintage is retained except per-run reports in the 90-day (UNCONFIRMED) artifact history. Only fade24 has an explicit revision detector (`scored_day_digests`, `compare_digests`, local `fade24_digests.json` / `fade24_revision_log.jsonl`).
- The G1 gate in `config/fast_gates_v1.json` compares two simulations on the same price data in the same run (the config's own `scope_note` says it tests modeled frictions, not real fills); a 0.999 paper-versus-V_ALL correlation is therefore not independent evidence of implementability.
- The paper account is a replay model, not a fill record. Real slippage and rejection cannot be measured without orders, which the repo does not place.

### Gaps
- No stored exchange bars, funding prints, order-book snapshots, positions/weights per day, or fills for the blend, human, paper-account, trend, cross-asset, zoo, TOM watches. No per-coin attribution.
- No per-run commit SHA or code/config hash in most reports.
- Artifact retention for the report artifacts is unset (default); history of what each daily run reported lives only in expiring artifacts.
- I could not see the contents of any actual GitHub artifact or the state of `main`'s scheduler.

## 3. What the monitor and dashboard read, and what they discard

### Takeaway
The headline monitor lines are a three-step derivation from the latest completed GitHub run's report JSON: cumulative compounded return of the primary book's daily series. The monitor then overwrites its own local snapshot, so no time series of snapshots exists beyond three SESSION_STATE.md lines and git history of that file.

### Cited Findings
- Derivation chain for "Multi-premia blend 16d -2.79%": `.github/workflows/multi-premia-blend-v1.yml` step "Run forward watch" writes `report.json` with `forward.S4_blend = summarize(fwd["S4_blend"].dropna(), nw_lags=5)`; `summarize` is in `src/orderflow_edge_lab/trend_portfolio_forward.py` (days = count of daily returns, `cumulative_return` = `(1+r).cumprod()[-1] - 1`, `annualized_sharpe` = mean/sd(ddof=1)*sqrt(365), Newey-West t with 5 lags, max drawdown from the compounded path). `scripts/dashboard_snapshot.py` `watch_entry` runs `gh run list -w <workflow name> -b research/payoff-geometry-v1-1 -s completed -L 1`, `gh run download <id>`, finds the report file, and stores per book `days, sharpe, t, cum, mdd, mean_bps` and a compounded `series` (last 400 points). `scripts/monitor_run.py` `summarize()` prints `"{tag} {days}d {100*cum:+.2f}%"` for the primary book named in the WATCHES list (blend primary `S4_blend`, human `H5`, core `combined`, vol-target `core_voltarget`, trend portfolio `plain`, paper account `paper`, zoo `M4_lottery_momentum`, fade24 `fade24_F1`, near-miss `cascade_1x`, tradfi `B2_weekend_fade_1x`, TOM `tom`). So the "-2.79%" is one primary book, compounded, not the mean across legs, and zoo "-3.33%" is only the M4 book while M2 is not shown.
- The monitor is a scheduled Claude task; its prompt is not in the repo. `scripts/monitor_run.py` does: `git pull --rebase`, `dashboard_snapshot.py`, `generate_status.py --snapshot`, writes one `- Monitor ...` line into `SESSION_STATE.md`, and commits/pushes SESSION_STATE.md and STATUS.md. It keeps only the 3 most recent monitor lines in SESSION_STATE.md (history is in git). Output directory is a local Windows path (`C:/Users/<user>/src/ofel_runs/dashboard`, username omitted), holding `summary.json`, `watches.json`, `runs.json`, and for fade24 `fade24_digests.json` and `fade24_revision_log.jsonl`. These files are overwritten each run (except the append-only revision log) and are not in the repo. ## 5. Known open findings and where their raw evidence lives

### Takeaway
The `_xs_weights` look-ahead finding is real in the code and is documented only as a SESSION_STATE.md paragraph; the same logic also sits in the headline blend's S2/S3 construction (my reading), so its scope is wider than the note states. No test or file quantifies its size.

### Cited Findings
- `SESSION_STATE.md` line 58: "FINDING (open, not fixed: frozen-watch code): `multi_premia_human_forward._xs_weights` (lines 41-44) requires the next day's open to mark a coin tradable: latest day's S2/S3 weights are 0 ... and historical books skip coins that delist the next day (one day of future listing knowledge, slightly flattering backtests)." Raw evidence: `src/orderflow_edge_lab/multi_premia_human_forward.py` lines 37-46 (`ret = opens.shift(-1)/opens - 1.0`; `sc = score.loc[d].where(opens.loc[d].notna() & ret.loc[d].notna())`).
- My reading of the code beyond the note: `src/orderflow_edge_lab/xs_premia.py` `run_xs` (line 53-54) uses the identical mask (`tradable = opens.loc[d].notna() & ret.loc[d].notna()`, with `ret = opens.shift(-1)/opens - 1.0`). `leg_returns` in `multi_premia_forward.py` calls `run_xs` for S2 and S3, so the blend's S2/S3 legs (development and forward S4_blend) and the development evaluation script share the same one-day look-ahead, and `paper_account.py` inherits `coin_targets` / `_xs_weights` via `multi_premia_human_forward`. The effect: a coin whose next-day open is missing (delisting, data hole, or the data end) is dropped from ranking on day d with knowledge of day d+1. Magnitude unknown; I found no file that measures it (no sensitivity run). The note's claim that it is "display only; replay recomputes" for the latest day and "slightly flattering" historically is not backed by a stored comparison.
- Other known open items in SESSION_STATE.md: funding-source mismatch (dev built with MEXC prices + Binance funding; MEXC funding history starts 2025-04-15, `research/fast_gates/RESULT.md`); old 10-coin book mostly long (crypto beta); effective N per cell about 16-31; tradfi B1 pending if a symbol is permanently unavailable on Yahoo (amendment 1 open rule); numpy pin differences; "Universal Existing Strategy Backtests" failing on main; `fade24` caveats (late-file immutability, `revised_days`, `matured_entry_cohort`); capacity at small coins; the Hyperliquid and OKX venues' independent check results (`research/fast_gates/hyperliquid_venue_check.json`).
- Look-ahead tooling: `scripts`/`tests/test_truncation_invariance.py` and `src/orderflow_edge_lab/truncation_check.py` (prefix-invariance check, noted in SESSION_STATE.md) and the near-miss reference's `equivalence` blocks (`max_abs_daily_net_diff` about 2e-16 for the near-miss sleeves) are the repo's look-ahead evidence; SESSION_STATE.md / `reports/Open source trading bot lessons.md` row 5 say the truncation check covers "the trend, VOL8, blend and cross-asset functions" as a proposal; I did not verify the test covers `run_xs` or `_xs_weights`.
